# 3. Design

## 3.1 Run topology and bounded iteration state machine

A quality run owns one immutable portable image identity, one p-limit object cache, up to five fresh worktrees, and one append-only artifact directory.

Each iteration follows this monotonic state machine:

```text
prepared
  → plan_called
  → plan_selected | plan_unavailable
  → apply_attempted
  → objective_validation_completed
  → review_called
  → defects_normalized
  → scored
  → appended
```

A stage failure does not erase prior evidence. The harness proceeds as far as possible:

- If a completed plan lane exists, application is attempted.
- If application partially modifies the worktree and exits nonzero, the partial diff is still tested and reviewed.
- If dependency installation fails, the semantic probe and `npm test` are marked blocked, but review still receives the failure evidence.
- If the plan MCP process fails entirely, application is blocked; review should still be attempted over the untouched pinned baseline plus the plan failure evidence.
- If the review MCP process cannot start or return a result, the iteration is finalized with provider/structural defects and cannot satisfy the stop condition.

Use **two independent stdio MCP server processes per iteration**:

1. A plan process mounted to the fresh, untouched p-limit worktree.
2. A review process started only after apply and tests, mounted to:
   - the post-apply p-limit worktree as root 0; and
   - a generated review-evidence directory as root 1.

This avoids depending on bind-mount change propagation, actor reentrancy, or selection reuse across the apply boundary.

At most four portable provider requests occur per full iteration:

- two for `context_builder(plan)`;
- two for `context_builder(review)`.

The five-iteration ceiling therefore permits at most 20 portable provider requests, excluding any calls made internally by the external apply adapter.

## 3.8 External apply-adapter contract

Portable remains read-only. Application is performed by a bounded external executable supplied with `--apply-command`.

Invocation contract:

```text
<apply-command> <absolute-path-to-apply-request.json>
```

Execution properties:

- `cwd` is the isolated p-limit worktree.
- No shell interpolation is used.
- stdin is closed.
- stdout and stderr are captured.
- The process runs in its own process group.
- On timeout, terminate the group, then kill it if necessary.
- Exit code 0 means the adapter claims completion; the harness still verifies the resulting Git state.

`apply-request.json` has a versioned shape:

```json
{
  "schema_version": 1,
  "run_id": "...",
  "iteration": 1,
  "repository": {
    "worktree": "...",
    "pinned_commit": "df476048d023ff868cd45b35ee47f5fb0ca2b25a"
  },
  "task": "...",
  "selected_plan": {
    "lane": "primary",
    "pair_id": "...",
    "model_raw_id": "...",
    "response_sha256": "...",
    "text": "..."
  },
  "prior_defects": [],
  "constraints": {
    "allowed_paths": [
      "index.js",
      "index.d.ts",
      "index.test-d.ts",
      "test.js",
      "readme.md",
      "package.json"
    ],
    "must_not_commit": true,
    "must_not_modify_outside_worktree": true
  }
}
```

The adapter’s stdout must be one JSON object describing its own provenance:

```json
{
  "status": "applied",
  "tool": "...",
  "tool_version": "...",
  "model": "...",
  "summary": "..."
}
```

Malformed adapter output is a structural defect even when the Git diff is usable.

The harness must derive changed paths and diff content from Git; it must never trust the adapter’s reported path list.

Apply success requires:

- adapter exit code 0;
- `HEAD` still equals the pinned commit;
- a non-empty tracked diff exists;
- all changed tracked paths are within `SELECTED_PATHS`;
- no non-ignored untracked files exist;
- `git diff --check` passes.

An adapter that commits, changes an out-of-scope file, or leaves a clean tree is unsuccessful.

Captured logs must be redacted before persistence using known secret environment values and common bearer-token patterns. Raw unredacted logs must not be written to the artifact directory.

### Independent AbortSignal semantic probe

Add a benchmark-only ESM probe at:

```text
benchmarks/p-limit-abort-signal-probe.mjs
```

It imports the modified worktree’s `index.js` and uses no project test helper. It must validate at least:

1. A running task starts under concurrency 1.
2. Multiple later tasks remain queued.
3. Aborting with a **falsy custom reason**, such as `0`, rejects queued tasks with exact identity.
4. The queued functions are never invoked.
5. `pendingCount` becomes zero.
6. A future submission rejects with the exact same reason.
7. The future function is never invoked.
8. The future rejection settles by the next microtask.
9. The already-running task remains unresolved until the probe explicitly releases it and then completes normally.
10. A pre-aborted signal rejects the first submission without invoking its function.
11. `rejectOnClear: true` still rejects manually cleared pending work with an `AbortError`.
12. A later signal abort still blocks future submissions with `signal.reason`.
13. The number of registered `abort` listeners does not grow with the number of submissions.
14. After abort, the signal’s listener count returns to its pre-limiter baseline.
15. All created promises are observed so the probe produces no unhandled rejection.

The probe prints one JSON object and exits 0 only when all checks pass. This specifically guards against the known truthiness and listener-observability defects that can survive a plausible-looking plan.

Realm-sensitive runtime validation, such as a bare `instanceof AbortSignal`, remains an explicit review criterion because Node cannot fully reproduce every browser-realm combination without adding dependencies.

```text
npm test
```

At this commit, that exercises XO, AVA, and `tsd` through the package script.

After all tests:

- capture the tracked diff again;
- verify its SHA-256 equals the post-apply diff;
- if tests changed tracked source, record `tests_mutated_source`;
- capture final status and `git diff --check`.

## 3.12 Quality score

Use a 100-point score. It is diagnostic; the stop condition remains stricter than a numerical threshold.

| Category | Points | Exact scoring |
|---|---:|---|
| Direct builder plan contract | 15 | 5 for MCP/tool/schema success; 5 for valid non-empty Primary projection; 5 for exact six-file complete context with no omissions/truncation |
| Plan pair health | 10 | 5 when both lane records are present, terminal, and pair status is consistent; additional 5 when both completed without provider errors |
| Apply isolation and success | 15 | 5 for valid adapter result and exit 0; 5 for pinned HEAD plus non-empty allowlisted diff; 5 for no untracked/out-of-scope changes and passing `git diff --check` |
| p-limit validation | 20 | 2 for `npm ci`; 8 for the independent semantic probe; 10 for full `npm test` |
| Direct builder review contract | 15 | 5 for MCP/tool/schema success; 5 for both review lanes terminal and completed; 5 for complete post-apply code/diff/evidence context with expected hashes and no truncation |
| Review findings | 10 | 10 when both parsed lanes have no findings; 5 when all findings are minor; 0 for major/critical findings or an unparseable lane |

An iteration may score partially after a stage failure. It may stop the loop only when it scores **100/100** and meets every hard done condition below.

## 3.13 Stop conditions

Stop with `stop_reason: "oracle_agreement"` only when one iteration satisfies all of the following:

- direct `context_builder(plan)` succeeds;
- both plan lanes complete;
- Primary is the selected plan;
- apply succeeds;
- the diff is non-empty and allowlisted;
- `git diff --check` passes;
- `npm ci` passes;
- the independent semantic probe passes;
- `npm test` passes;
- tests do not alter the tracked diff;
- direct `context_builder(review)` succeeds;
- both review lanes complete;
- review context contains the exact post-apply code, diff, plan, test, and provenance hashes without omission or truncation;
- both review payloads parse;
- both lanes return:
  - `workflow_verdict: correct`
  - `implementation_verdict: correct`
  - `overall_verdict: correct`
  - an empty `findings` array;
- provenance is complete;
- score is 100.

Otherwise start the next fresh iteration with the normalized feedback. After iteration 5, finalize with `stop_reason: "max_iterations"` even if both lanes agree on an incorrect verdict.

## 3.17 Concurrency, cancellation, and lifecycle

The Python harness itself remains sequential. The only intended concurrency is the existing Primary/Secondary execution inside `HeadlessOracleWorkflow`.

- match JSON-RPC responses by request ID;
- close stdin in `finally`;
- wait for process exit;
- record return code, timeout status, and redacted stderr;
- do not retry a provider call inside an iteration;
- use a new iteration for another attempt.

- use independent process groups;
- terminate the whole group on timeout;
- record timeout as a defect;

- the bare Git object cache;
- the unresolved-defect text passed into the next plan prompt;

# 5. Risks and migration

## Benchmark interface and artifact compatibility

The new artifacts use schema version 2 and a directory layout rather than the legacy single JSON shape. Preserve `benchmarks/p-limit-portable.json` unchanged as historical evidence. Support `--workspace` and `--timeout-seconds` only as documented aliases so existing local invocations fail clearly rather than silently changing meaning.

## Live-model nondeterminism

Plan and review output may vary despite identical inputs. Mitigation:

- fresh pinned baseline each iteration;
- immutable image identity;
- exact prompt and response hashes;
- no automatic provider retry;
- both raw lanes retained;
- hard objective gates;
- maximum five iterations.

## External apply-agent trust

Working-directory confinement and post-apply Git validation detect accidental scope violations but do not sandbox a malicious host executable. The recommended adapter should itself run in a container or OS sandbox with only the iteration worktree writable. The benchmark must never grant the apply adapter write access to the portable repository or source fixture.

## Network and package availability

Initial Git fetch and `npm ci` require network access unless caches are already populated. Distinguish acquisition/install failures from implementation failures in the defect ledger. Never reinterpret a network failure as a code defect.

## Review JSON brittleness

Strict JSON improves agreement quality but may cause otherwise useful prose to be scored unparseable. This is intentional: the stop decision must be machine-auditable. Raw text remains available for diagnosis and can be fed back as an output-contract defect.

## Artifact size and disk use

Five worktrees, two full plan results per iteration, diffs, and test logs can be sizable. Bound review-context logs but retain complete redacted logs as artifacts. Do not auto-delete evidence. The run manifest records byte counts.

## Secret exposure

Do not record complete process environments, Docker image config, API-key values, or key hashes. Redact captured logs before writing them. Record only credential source names and presence.

## Dirty portable worktree

Before the run, record the portable repository’s current `git status --porcelain=v2`. After the run, verify no path outside the configured artifact root and ignored `.build` work area changed. Never invoke reset, clean, restore, checkout, or stash against the portable repository.

### 3.7 Direct review invocation

**Goal:** review the **resulting** implementation, not the pre-apply plan context alone.

**Harness-prepared review selection (portable has no git tool):**

1. Write into the worktree (or a sibling review-mount directory) files the MCP can select, for example:

2. Mount that tree read-only into Docker `/workspace`.
3. `manage_selection` set to those review files (full mode).
4. `context_builder` `response_type: "review"` with instructions that require:
   - Explicit verdict line per lane: `VERDICT: PASS` or `VERDICT: FAIL`
   - Bullet findings with severity `blocker|major|minor`
   - Separate judgments for **workflow harness correctness** vs **p-limit AbortSignal implementation quality**
   - Confirmation that running tasks are untouched, pending/future rejected with `signal.reason`, `rejectOnClear` preserved, no abort-listener leaks

**Structural review gates:** same pair envelope rules as plan; `response_type == "review"`; `status` `response_generated` or `response_failed`.

**Semantic parsing of agreement:** regex/`VERDICT:` lines from **both** `oracle_results.primary.response` and `.secondary.response`. Agreement = both lanes `status==completed` **and** both verdicts `PASS` **and** no blocker findings in either lane. If a lane omits `VERDICT:`, treat as non-agree (score 0 for agreement).

### 3.8 Quality rubric / score

**Per-iteration score (0–100), fixed weights:**

| Component | Points | Pass rule |
| --- | --- | --- |
| Direct plan success | 15 | Tool OK, `response_type=plan`, Primary completed **or** documented apply-from-Secondary path only if Primary failed |
| Both lanes terminal | 10 | Both lane statuses present and terminal |
| Apply success | 15 | `ApplyOutput.ok`, non-empty meaningful change **or** justified no-op only if plan claimed no code change (unexpected here → fail) |
| p-limit tests | 20 | `npm test` exit 0 |
| Direct review success | 15 | Tool OK, `response_type=review`, both lanes terminal |
| Review findings quality | 10 | No blocker findings; majors counted (each major −2 from this bucket, floor 0) |
| Lane agreement | 10 | Both `VERDICT: PASS` and no blockers |
| Provenance completeness | 5 | Image digest, timeouts, models, config route, applied_lane, commit, worktree id all present |

**Binary “done” for an iteration:** score ≥ 95 **and** lane agreement **and** tests_ok **and** apply_ok **and** both plan+review pairs `pair_status == completed`.

**Campaign done:** any iteration meets binary done, **or** five iterations completed (record `stopped_reason: agreement|max_iterations`).

**Baseline procedure (iteration 0 / first row)**

1. Rebuild/use image; record digest.
2. Acquire/verify p-limit commit.
3. Run one full iteration without requiring prior scoreboard history.
4. Also keep a one-shot JSON snapshot analogous to today’s artifact but with plan via `context_builder(plan)` for regression comparison (`benchmarks/p-limit-portable-quality-baseline.json`).

## 5. Risks and migration

- **Apply nondeterminism:** different apply agents yield different code; mitigate by recording plan text + diff + lane; compare scores across campaigns carefully.
- **VERDICT prompt-sensitivity:** models may omit the token; mitigate with explicit instruction + fail-closed agreement.
- **Provider cost/time:** 5 iterations × (plan pair + review pair) = up to **20** live completions; document and allow `--max-iterations`.
- **Secret leakage:** never dump `opencode.docker.json` apiKey; redact Authorization in any captured HTTP debug.
- **Rollback:** harness-only; delete new scripts/scoreboard rows if needed; no schema migration in Swift.
- **Dirty tree:** additive files only; never reset portable git state.
