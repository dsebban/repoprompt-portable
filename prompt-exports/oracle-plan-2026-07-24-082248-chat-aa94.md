# 3. Design

## 3.1 Campaign and iteration model

### Unit of measurement

One benchmark invocation represents one complete quality iteration:

```text
pinned pristine p-limit
  → pristine npm test
  → direct context_builder(plan), both lanes
  → deterministic plan selection
  → OpenCode applies selected plan in disposable copy
  → scope checks
  → independent semantic probe
  → full npm test
  → direct context_builder(review), both lanes
  → normalized findings and agreement
  → JSON artifact
  → append-only scoreboard row
```

Baseline is iteration `0`. Hardening iterations are `1` through `5`.

### Stop rules

Record three distinct agreement values:

- `plan_verdict_agreement`: both plan trailers have the same `ready|needs_changes` verdict.
- `review_verdict_agreement`: both review trailers have the same `pass|changes_requested` verdict.
- `review_acceptance_agreement`: both review lanes:
  - completed,
  - produced valid structured trailers,
  - returned `verdict: "pass"`,
  - reported no blocking findings,
  - marked all required semantic dimensions as passing.

The campaign stops successfully only when:

```text
review_acceptance_agreement
AND pristine npm test passed
AND post-change npm test passed
AND every independent semantic probe case passed
AND scope/provenance/worktree gates passed
```

Agreement that the implementation is defective does not stop the campaign successfully.

If iteration `5` does not reach this state, append the final result with decision `stop_iteration_cap` and do not begin iteration `6`.

### One-attributed-change rule

For iteration `N > 0`:

- `--candidate-id` and `--attributed-change` are required.
- The previous iteration artifact is required.
- Image IDs, provider endpoint identity, model IDs, p-limit commit, timeout settings, and probe version must match the baseline.
- Only one benchmark hardening candidate may be landed between two iterations.
- p-limit always starts again from the pinned pristine commit; no implementation diff carries forward.

This preserves causality between benchmark hardening and observed correctness.

The Swift server still dispatches Primary and Secondary concurrently internally.

### Phase algorithm

1. Parse and validate all arguments.
2. Require a non-empty host `OPENCODE_API_KEY`.
3. Resolve portable and Node image identities.
4. Validate the source repository contains the pinned commit.
5. Capture a portable-worktree preservation fingerprint.
6. Create a disposable clone at the pinned commit.
7. Verify exact commit, tree hash, and clean status.
8. Run pristine `npm ci` and `npm test`.
9. Remove `node_modules` before exposing the workspace to the application model.
10. Run direct builder plan.
11. Parse and select a lane plan.
12. Apply the selected plan.
13. Capture scope and diff evidence.
14. Run post-change `npm ci`, semantic probe, and `npm test`.
15. Build bounded review evidence.
16. Run direct builder review.
17. Normalize both review lanes and compute score/agreement.
18. Write the JSON artifact atomically.
19. Append the scoreboard row and detailed record.
20. Verify the portable worktree fingerprint is unchanged except for declared output and scoreboard paths.
21. Clean disposable containers, secret files, and workspace unless retained.
22. Exit according to the stop result.

Partial pseudocode:

```text
if pristine_test_failed:
    record invalid_environment
    do not call plan or application
elif plan_pair_not_completed or no_eligible_plan:
    record plan_failure
    do not apply
else:
    apply selected plan
    run every deterministic verification
    run review even when apply/test/probe failed
    compute acceptance only after all evidence exists
```

Review should still run after a failed application, scope check, probe, or `npm test`, provided readable changed files exist. Those failures are valuable review evidence.

## 3.9 Independent AbortSignal conformance probe

### File

Add `benchmarks/p_limit_abortsignal_probe.mjs`.

### Purpose

This is an external behavioral oracle. It imports the modified local `index.js` but is not copied into p-limit’s committed source and is not part of the plan-generated tests.

### Invocation

Run in the resolved Node image with network disabled:

```text
node --expose-gc /benchmark/p_limit_abortsignal_probe.mjs /workspace/index.js
```

Mount the probe read-only at `/benchmark/p_limit_abortsignal_probe.mjs`.

The probe emits one JSON object with:

```json
{
  "schema_version": 1,
  "passed": true,
  "cases": [
    {
      "id": "queued_exact_reason",
      "passed": true,
      "details": {}
    }
  ]
}
```

Exit `0` only when all cases pass; otherwise exit nonzero after emitting the complete case matrix.

### Required cases

1. **`queued_exact_reason`**
   - Hold one task in the running state.
   - Queue at least two tasks.
   - Abort with a unique object.
   - Both queued promises reject with the identical object.
   - Their functions never run.
   - `pendingCount` becomes `0` synchronously after `abort()`.

2. **`future_immediate_rejection`**
   - Submit after abort.
   - Returned promise rejects with the exact reason.
   - Function is never invoked.
   - `activeCount` and `pendingCount` do not increase.

3. **`running_untouched`**
   - Running task is not rejected or interrupted by limiter abort.
   - It returns its original value after an explicit deferred release.
   - `activeCount` eventually returns to `0`.

4. **`pre_aborted_signal`**
   - Construct with a pre-aborted signal.
   - No submitted function runs.
   - Rejection reason is exact.
   - No abort listener remains registered.

5. **`falsey_reason_matrix`**
   - Independently cover `null`, `false`, `0`, `""`, and `NaN`.
   - Compare with `Object.is`, not truthiness or `Error.message`.

6. **`reject_on_clear_enabled`**
   - With an un-aborted signal and `rejectOnClear: true`, `clearQueue()` rejects pending work with an `AbortError`.
   - The signal remains un-aborted.
   - A later submission is still accepted.
   - A later signal abort still uses its own exact reason.

7. **`reject_on_clear_disabled`**
   - Existing default behavior remains: queued tasks are discarded and their returned promises remain unsettled.
   - Future submissions continue to work.
   - The discarded functions never run.

8. **`listener_lifecycle`**
   - Use Node’s `getEventListeners(signal, "abort")` and inspect `signal.onabort`.
   - No listener immediately after limiter construction.
   - No listener while only running work exists and no work is queued.
   - At most one listener while pending work exists.
   - Listener count returns to zero after:
     - natural queue drain,
     - `clearQueue()`,
     - signal abort.
   - Repeated queue waves never accumulate listeners.

   This explicitly rejects the weaker claim that `{once: true}` alone prevents a listener from being retained forever when a signal never aborts.

9. **`map_propagation`**
   - `limit.map()` after abort rejects with the exact reason.
   - Mapper is not invoked.

10. **`limit_function_propagation`**
    - `limitFunction(..., {signal})` inherits the same abort semantics.
    - Running invocation remains untouched and future invocation rejects.

### Static contract checks

The Python harness separately checks:

- Required modified files:
  - `index.js`
  - `index.d.ts`
  - `index.test-d.ts`
  - `test.js`
  - `readme.md`
- `index.d.ts` contains an optional readonly `AbortSignal` option.
- `index.test-d.ts` covers valid and invalid `signal` types.
- README documents:
  - queued/pending rejection,
  - exact `signal.reason`,
  - future submissions,
  - running work remaining untouched,
  - distinction from `rejectOnClear`.
- Dependencies and package scripts are unchanged.

These static checks are supporting evidence; `npm test` remains authoritative for lint, AVA, and `tsd`.

## 3.12 Correctness rubric

The score is diagnostic; acceptance remains all-gates-required.

| Area | Points | Exact condition |
|---|---:|---|
| Provenance and isolation | 10 | Images resolved and run by ID; explicit sanitized provider config; exact p-limit commit/tree; portable worktree guard preserved; pristine npm test passes. |
| Plan transport | 10 | Direct `context_builder(plan)` returns `pair_status: completed`, both lane statuses completed, models match, and context is complete. |
| Plan parsing and selection | 5 | Both trailers parse and one eligible plan is selected under the deterministic policy. |
| Application and scope | 10 | Writer exits zero, produces a non-empty diff, and touches only the five permitted product files. |
| Semantic probe | 30 | Ten probe groups, three points each. No partial credit inside a group. |
| Full package test | 15 | Post-change `npm test` exits zero without timeout. |
| Types and documentation | 5 | Static declaration, type-test, required-file, dependency, and README checks pass. |
| Review transport and parsing | 5 | Direct `context_builder(review)` completes both lanes with valid trailers and complete context. |
| Review verdict agreement | 5 | Both normalized verdicts are equal. |
| Review acceptance agreement | 5 | Both independently accept with no blocking findings and all deterministic gates pass. |
| **Total** | **100** | |

`end_to_end_pass` is true only at 100 points and with every mandatory gate explicitly true. Do not treat a lower score as a pass.

A single correctness run is the baseline sample. Do not calculate medians or average stochastic model outcomes. When a same-code rerun is needed because of provider instability, append it as a correction/retry record rather than replacing or averaging the earlier row.

## 3.15 Failure and lifecycle behavior

| Failure | Required behavior |
|---|---|
| Missing `OPENCODE_API_KEY` | Fail preflight before cloning or scoreboard mutation. |
| Image not present or inspect fails | Fail preflight; never fall back to a mutable or different image. |
| Pinned p-limit commit absent | Fail preflight; do not fetch automatically from inside the benchmark. |
| Pristine `npm test` fails | Record `invalid_environment`; skip plan/application/review. |
| Plan MCP tool error or partial lane failure | Record raw result; do not apply a plan. |
| Invalid plan trailers | Select the other eligible lane; fail the iteration if neither is eligible. |
| Application timeout/nonzero exit | Capture diff/logs; run verification/review when readable files remain. |
| Scope violation | Run verification/review for diagnostics but force acceptance false. |
| Probe or `npm test` failure | Run review with failure evidence; force acceptance false. |
| Review partial failure or invalid trailer | Record available lane; agreement false. |
| Artifact write failure | Do not append scoreboard. |
| Scoreboard append failure | Keep artifact and exit harness failure; never rewrite earlier rows. |
| SIGINT/SIGTERM | Force-remove named child containers, delete secret files, preserve existing artifact files, and optionally retain workspace. |

Provider responses arriving in reverse order are handled by lane keys, never by output position. Duplicate iteration/run IDs are rejected during scoreboard append.

## 3.16 Ranked hardening candidates

These are iteration candidates, not baseline instrumentation. Apply only one at a time.

### 1. Adversarial semantic plan instructions

**Trigger:** Selected plans or resulting implementations fail exact-reason, falsey-reason, or listener-lifecycle probe cases.

**Change:** Extend only the plan request text with the explicit non-negotiable semantic matrix and reject known shortcuts:

- Aborted state cannot be inferred from reason truthiness.
- Primitive reasons must be compared by identity/value rather than `Error.message`.
- `{once: true}` alone does not address a signal that never aborts.
- Listener presence must be tied to pending work and cleaned when the queue drains or clears.

**Expected effect:** Highest likelihood of preventing incorrect implementation before application.

**Risk:** Low. It changes prompt guidance, not product behavior or scoring.

### 2. Evidence-rich review packet

**Trigger:** Deterministic checks fail but one or both review lanes return `pass`, or lane findings diverge substantially.

**Change:** Expand only `.repoprompt-benchmark/review-evidence.json` to include:

- Bounded unified diff with base and current file hashes.
- Exact failed probe case details.
- Relevant npm test failure excerpts.
- Required-versus-actual changed-file matrix.

**Expected effect:** Improves review grounding and lane agreement.

**Risk:** Low to medium. The packet must remain within the context budget and must not crowd out source files.

### 3. Category-only prior-review feedback

**Trigger:** Two consecutive iterations fail in the same normalized finding categories.

**Change:** Append the union of prior blocking category IDs—not synthesized prose—to the next plan request as “previously unresolved dimensions.” Keep both raw prior lane responses in artifacts but do not merge them into a new plan.

**Expected effect:** Focuses the next independent plans without hiding lane disagreement.

**Risk:** Medium. It can overfit to the prior run, so use only after repeated category-level evidence.

# 5. Risks and migration

## Benchmark CLI compatibility

The existing prototype has no published compatibility contract, but retain its primary arguments. `--timeout-seconds` remains a deprecated alias so existing invocations fail only when they omit newly necessary quality-loop inputs or violate validation.

The semantic meaning of `--workspace` becomes explicit: it is a source Git repository that the harness clones, never the directly mutated target.

## Legacy artifact compatibility

`benchmarks/p-limit-portable.json` remains readable evidence but does not satisfy the new schema. Do not migrate or overwrite it. New artifacts use `schema_version: 1`.

## Model nondeterminism

The provider API does not expose a seed through the current portable contract. Treat every iteration as an attributed trial, not a statistical sample. A transport retry is appended as a separate correction row.

## OpenCode application behavior

OpenCode may exit successfully without producing a valid diff, may touch files outside scope, or may echo sensitive material. The harness therefore:

- Verifies non-empty allowlisted changes.
- Redacts all captured output.
- Treats application exit as evidence, not success.
- Uses deterministic tests and review afterward.

Validate the pinned `opencode 1.18.4` `run` behavior with the first disposable baseline rather than introducing a fallback writer.

## Listener-lifecycle interpretation

The benchmark defines leak-free behavior observably: no abort handler remains when there is no queued work. This is stricter and more useful than merely using `{once: true}`. It remains implementation-neutral: any strategy passing the listener and semantic cases is acceptable.

## Context budget

The review evidence packet could crowd out source. Cap it at 256 KiB and fail closed if the complete seven-entry review selection does not fit within `max_context_bytes`.

## Image drift

Tags are allowed only as user-facing inputs. Every actual run uses resolved image IDs. If an ID changes between iterations, start a new baseline instead of comparing scores.

## Suspected product defects

A live failure is escalated to product scope only when reproduced using the deterministic fixture workflow in `Scripts/smoke_portable_oracle_docker.sh` and encoded in a focused Swift test. Examples include:

- Missing lane despite two successful fixture responses.
- Cross-lane context mismatch.
- Incorrect Primary projection.
- Invalid `pair_status`.
- Context selection mutation during a generated call.
- Explicit provider timeout not reaching the provider.

A weak plan, an incorrect p-limit implementation, or review disagreement remains benchmark/model behavior.

#### F. Semantic rubric (machine-checkable; primary metric)

Transport success is necessary but insufficient. After apply:

**R1 — Static/source checks (cheap, deterministic):**

| ID | Check | Pass rule |
|---|---|---|
| R1.1 | Options accept `signal` | `index.d.ts` `Options` includes `signal?: AbortSignal` |
| R1.2 | Runtime extracts signal | `index.js` options destructure includes `signal` |
| R1.3 | Abort rejects pending with reason | Abort path calls `reject(...)` with `signal.reason` (not only `AbortSignal.abort().reason` unless reason is that) |
| R1.4 | Generator rejects when aborted | `generator` / limit entry rejects before enqueue when aborted |
| R1.5 | Running tasks untouched | No abort of in-flight; no `AbortSignal` passed into user fn unless docs say so (default: do not cancel running) |
| R1.6 | Listener lifecycle | `addEventListener('abort', …, {once: true})` **or** matching `removeEventListener`; document that never-abort retains listener until limiter GC (acceptable) vs leak across many limiters (fail if listener added without once/remove) |
| R1.7 | `rejectOnClear` independent | Existing clearQueue path unchanged in spirit; tests still assert AbortError on clear when enabled |
| R1.8 | Types tests updated | `index.test-d.ts` has signal accept + `expectError` on bad signal |
| R1.9 | README documents signal | `readme.md` has a `signal` section |

Implement R1 as regex/AST-light scans in Python under `benchmarks/`; false negatives allowed to be conservative (fail open to human note), but R1.1/R1.2/R1.8/R1.9 must be strict.

**R2 — Behavioral tests via upstream suite:**

- Command: `npm test` ≡ `xo && ava && tsd` in writable copy (Node `>=20`).
- Pass: exit 0.
- Record stdout/stderr tails in artifact (cap 64 KiB each).

**R3 — Harness-owned behavioral probes (minimal; only if upstream tests miss AbortSignal):**

Add **one** file only inside the **writable copy**, never in portable:

`test-abort-signal.harness.js` (AVA) covering:

1. Abort while one running + two pending → running fulfills; pendings reject with **exact** reason (including falsey `controller.abort(0)` / `undefined` default AbortError); `pendingCount === 0`; later `limit(fn)` rejects immediately with same stored reason.
2. Pre-aborted signal at construction → submissions reject; fn never called.
3. Custom Error reason → `t.throwsAsync(..., {is: error})`.
4. `rejectOnClear: true` still rejects with AbortError name on `clearQueue`, independent of signal.

**Decision:** Prefer teaching the **applied plan** to extend `test.js` so harness file is unnecessary; if after apply R2 passes but R1.3–R1.5 are weak, inject harness file for that iteration only and record `harness_tests_injected: true`.

**Primary metric (single number for the scoreboard):**

```text
correctness_score = 100 * (
  0.15 * plan_pair_ok +          # both lanes completed plan
  0.25 * rubric_r1_fraction +    # R1 checks passed / total
  0.35 * npm_test_ok +           # 1 or 0
  0.15 * review_pair_ok +        # both lanes completed review
  0.10 * review_agreement_ok     # normalized agreement true
)
```

Stop criterion is **not** maximizing this score alone; see §3.6.

#### G. Review agreement schema (resolves “lanes agree”)

Do **not** treat Primary `response` as agreement. Normalize each review lane into:

```text
NormalizedReview {
  lane: primary|secondary
  verdict: "accept" | "reject" | "inconclusive"
  finding_fingerprints: set[str]   # normalized defect ids
}
```

**Normalization algorithm:**

1. Lowercase lane text.
2. Extract finding lines: bullets/numbered items containing defect verbs (`bug`, `missing`, `incorrect`, `leak`, `should`, `fail`, `broken`) or explicit `severity:`.
3. Map each finding to a closed taxonomy fingerprint when possible:

```text
pending_reason | future_reject | running_untouched | preaborted
| falsey_reason | reject_on_clear | listener_lifecycle
| types_docs | tests_gap | other:<sha1-of-normalized-sentence>
```

4. Verdict rules:
   - `accept` if text contains an explicit accept phrase (`lgtm`, `no blocking`, `looks correct`, `approve`) **and** zero taxonomy hits in `{pending_reason, future_reject, running_untouched, listener_lifecycle}`  
   - `reject` if any of those high-severity fingerprints present or explicit reject phrase  
   - else `inconclusive`

**Agreement:**

```text
review_agreement =
  both verdicts identical
  AND symmetric difference of finding_fingerprints is empty
  OR (both accept AND high-severity fingerprints empty on both)
```

Plan-phase “agreement” (optional early exit, **not** stop by itself):

```text
plan_agreement = both plan lanes pass the same structural checklist scan
                 AND chosen policy did not need manual override
```

**Stop when (locked):**

1. `review_agreement == true` **and** `npm_test_ok` **and** all **must-pass** R1 checks (R1.1–R1.5, R1.7–R1.9) pass, **or**
2. Iteration `N == 5` (hard cap), **or**
3. Two consecutive iterations with `plan_pair_ok == false` or provider `pair_status != completed` (escalate; do not keep burning tokens).

Raw lane responses always retained under artifacts; disagreement must remain auditable.

#### J. Concurrency / lifecycle / errors

- One MCP Docker process per phase; close stdin; assert exit 0 / not timed out (same as smoke).

- Duplicate abort events: irrelevant to harness; rubric notes product `{once:true}` expectation.

#### K. Algorithm — one iteration

```text

1. writable = copy(pristine_commit) → iter-N

7. npm = run_npm_test(writable)
8. review_pair = MCP review against writable
9. agreement = normalize_review(review_pair)
10. score = correctness_score(...)
11. append artifacts + scoreboard row
12. if stop predicate → halt else N+1
```
