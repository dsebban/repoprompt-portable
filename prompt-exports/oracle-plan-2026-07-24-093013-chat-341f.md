### Listener lifecycle

Both iteration-1 plan lanes marked `listener_lifecycle` as covered:

- Primary proposed `{once: true}` as automatic cleanup after abort.
- Selected Secondary also relied on `{once: true}`, adding only an internal queued-item guard.

```text

```

The deterministic probe failed immediately because the listener count was `1` where initial idle required `0`. The hardening must therefore use explicit `*_listener_count` terminology and must not invent an `activeCount` requirement from the review wording.

A queue-scoped listener also creates an important interaction the old plans missed: abort can occur while only running work exists, when no listener should be installed. Future submissions must therefore read the current `signal.aborted` and `signal.reason` state rather than relying solely on a flag written by the abort listener.

### Unobserved expected rejections

The generated `pending count is zero after abort` test created two pending promises and discarded their references before calling `controller.abort()`. Abort synchronously rejected both promises before any rejection handlers were attached.

The missing planning rule is temporal: every promise intentionally expected to reject must have a rejection observer attached **before** `abort()` or rejecting `clearQueue()` is invoked, including tests whose primary assertion concerns only `pendingCount`.

The transport, deterministic probe, application isolation, scope checker, and post-change review already performed their intended roles. The defect occurred earlier: `PLAN_INSTRUCTIONS` permitted shallow semantic self-certification, and `parse_plan_lane()` treated those self-certifications as eligible.

## 3.3 Behavioral semantics forced into the selected plan

The structured contract establishes this listener state machine without dictating an implementation data structure:

| Limiter state | Required total abort-listener count |
|---|---:|
| Immediately after construction | 0 |
| Constructed with a pre-aborted signal | 0 |
| One or more running tasks, no queued tasks | 0 |
| One or more queued tasks with an un-aborted signal | 1 |
| After the final queued task is promoted or the queue naturally drains | 0 |
| After `clearQueue()`, regardless of `rejectOnClear` | 0 |
| After abort | 0 |
| Across repeated queue waves | Never more than 1; returns to 0 after each wave |

The contract deliberately does not prohibit `{once: true}`. It prohibits treating it as the sole lifecycle strategy. A valid plan may combine `{once: true}` with explicit removal on every non-abort queue-empty transition.

The rejection-observation contract remains test-framework neutral. Valid plans may use immediate capture wrappers, `.catch()`/`.then()` observers, or assertions created before the trigger. They may not leave expected rejection promises unobserved until after synchronous abort or clear processing.

# 5. Risks and migration

## Over-constraining implementation design

The contract requires externally observable listener counts already asserted by the deterministic probe, but it does not prescribe queue-item fields, helper names, Promise structure, or a specific listener API. `{once: true}` remains permitted as supplemental abort-path cleanup.

The per-submission signal check is necessary rather than stylistic: without a persistent running-only listener, aborts occurring while the queue is empty would otherwise be missed for future submissions.

## Plan schema and parser compatibility

The nested `<portable_plan_result>` contract intentionally breaks from v1 to v2. Historical artifacts remain append-only and require no migration because the harness does not reparse their raw plan responses during normal execution.

Only the nested plan-result schema changes. The following remain at version 1:

- top-level benchmark artifacts;
- `<portable_review_result>`;
- correction artifacts.

An older harness would not understand a v2 plan response if asked to reparse one. Rollback therefore means reverting the prompt and parser together, not mixing versions.
