# 2. Current-state analysis

## 2.1 Ownership and data flow that the UI must reuse


`WorkspaceSelectionSnapshot` (`selectedPaths`, `autoCodemapPaths`, `slices: [String: [LineRange]]`, `codemapAutoEnabled`) is the single mutable state the UI needs, owned by the `WorkspaceSelectionStateStore` actor, mutated only via `persist(_:for:source:)` with `source: .headless`, and observable via `changes()` (an `AsyncStream` we will **not** use — see §3.5).

# 3. Design

## 3.1 Service boundary decision (three options compared)

**Option 2 — in-process adapter over `HeadlessToolCatalog.call` + JSON parsing. Rejected.** Concrete blockers from the code, not style preferences:
- No tool returns a flattened file list; the UI would have to parse `get_file_tree` ASCII output or invent a `file_search` pattern. Wrong by construction.
- `manage_selection`/`file_search` return `displayPath` strings; toggling requires display→absolute inversion, i.e. re-implementing `parseRootQualifiedPath` in the UI (a parallel code path, and a path-safety-relevant one).
- `context_builder` clarify JSON-encodes up to 1 MiB of source into a string the UI immediately decodes; typed `entries`/`omissions` fidelity is reduced to string reasons.
- Errors arrive as `isError == true` plus a `code` string, so the UI needs a second, untyped error schema; contract drift becomes a runtime bug instead of a compile error.

**Option 3 — subprocess stdio MCP / JSONL. Rejected.** The CLI contract already documents “Separate processes do not share selection.” A long-lived desktop would have to own a persistent MCP session: framing, initialize handshake, timeouts, reaping, version matching against a co-installed `repoprompt-headless`, plus piping 1 MiB contexts. It buys nothing that in-process composition doesn’t already give (the CLI is the existing precedent for direct in-process catalog use) and it dilutes lifecycle ownership of the one `WorkspaceSelectionStateStore` actor.

**Option 1 — narrow public typed facade inside `RepoPromptHeadless`, sharing extracted internals with the catalog. Chosen.** It is the only option that keeps one implementation of path resolution, selection mutation limits, and the `incomplete_workspace_context` gate; the facade lives in the same target, so `HeadlessWorkspaceContextBuilder`, `HeadlessOracleWorkflow`, and `OpenAICompatibleOracleProvider` stay internal. The catalog keeps 100% of its JSON shaping, so the MCP contract is preserved by construction and proven by leaving every existing test file unmodified.

Accepted cost: exposing `RepoPromptHeadless` as a library product transitively exposes/links `MCP` + `Logging` to the desktop binary. Both are pure Swift with no Apple dependencies. Splitting the target to avoid that would be a much larger refactor against the existing test suite; not worth it for slice 1.

## 3.3 New public facade: `PortableWorkspaceService`

Files: `RepoPromptHeadless/Service/PortableWorkspaceService.swift`, `RepoPromptHeadless/Service/PortableWorkspaceTypes.swift`.

Kind: `public actor`. Actor is correct because it owns mutable index state and serializes access to the `RepoPromptSession`/`WorkspaceSelectionStateStore` actors while keeping file I/O and context rendering off the GTK main thread.


Startup is fail-fast **before** any GTK work, matching CLI exit codes: usage errors → `HeadlessExitCode.usage` (64) with usage text on stderr; invalid roots or malformed `REPOPROMPT_ORACLE_*` → `HeadlessRuntimeError.exitCode` (78) with the message on stderr. `--help` prints and exits 0 without touching a display. **Threading / lifecycle**

| Step | Context |
|---|---|
| view body, `@State` writes | GTK main thread |
| `.task` initial load, button actions | `Task` created on main; body suspends |
| `refreshFileIndex`, `toggle/set/clearSelection`, `buildContext`, `askOracle` | `PortableWorkspaceService` actor executor (off main) |
| `WorkspaceSelectionStateStore.persist/snapshot` | its own actor, awaited from the service |
| Oracle lanes | two `async let` child tasks; `URLSession`/FoundationNetworking |
| result application | `await MainActor.run { shell.reduce(event) }` |

**Ordering / duplication / dropping.** Every activity is started with `let g = shell.begin(...)`, which bumps `generation` after cancelling `work.task`. The async closure always emits exactly one terminal event carrying `g`; `reduce` drops terminal events whose generation ≠ `state.generation`. Duplicated terminal events are idempotent (assignment, not append). Because a new activity always cancels the previous task and bumps generation, no dropped event can leave `activity` stuck.

We deliberately do **not** subscribe to `WorkspaceSelectionStateStore.changes()`: the desktop process has exactly one mutator, so the returned `PortableSelectionSummary` from each mutation is authoritative. Adding a stream would be indirection with no consumer.

**Byte budget.** The desktop uses the fixed `PortableWorkspaceService.maximumContextByteBudget` (1 MiB, the builder’s validated ceiling) for both build and ask, so `truncated` only occurs for genuinely oversized selections. No user-facing budget control in slice 1.

**Errors and edge cases.** Zero roots → rejected by `validatedRoots` at launch (exit 78). Empty selection → builder emits “No readable files are selected.”, `isCompleteForProvider == true`; Ask Oracle is allowed and the UI shows a note. Empty instructions → Ask Oracle button disabled (mirrors the workflow’s non-empty requirement). File deleted after indexing → `not_found` omission; build shows it, ask fails with `incompleteWorkspaceContext(preview)` and the UI renders the omission list plus “deselect or reload”. Selection > 1024 files → `selectionLimitExceeded`. Cancel → `.cancelled`, status “Cancelled.”, selection/instructions/last result untouched. Index above `fileIndexCap` → `indexTruncated == true` surfaced as a sidebar label.

**Performance.** Index build is O(files) I/O once per launch/reload on the service actor. Filtering is O(n) substring matching per keystroke on the main thread with `n ≤ fileIndexCap` and a 500-row render limit; if profiling shows lag, pre-lowercasing display paths in the index is a follow-up item, not slice 1.

Implement the Linux desktop as a **nested Swift package under `LinuxDesktop/`**, pinned to **SwiftCrossUI 0.8.0**, so GTK and UI dependencies never enter the root headless package’s dependency resolution or release image. Add one additive root library product, `RepoPromptHeadless`, plus a narrow typed `PortableWorkspaceService` inside that existing target. The service becomes the shared implementation boundary for selection, context rendering, and Oracle execution; `HeadlessToolCatalog` continues owning the MCP schemas and exact JSON serialization but delegates those behaviors to the service. The desktop remains deliberately small: one configured workspace, a flattened path-searchable file list, explicit full-file selection and clear, a plain task editor, local context preview, and a fixed dual-lane **Generate Plan** provider action. There is no clipboard integration, folder picker, native tree, rich editor, tabs, presets, git/apply flow, Agent Mode, fallback transport, or desktop container.

# 2. Current-state analysis

## Package and release graph

The root `Package.swift` currently has:

- One public library product: `RepoPromptCore`.
- Two executable products: `repoprompt-headless` and `repoprompt-portable-cli`.
- An internal `RepoPromptHeadless` target used by both executables.
- Only `swift-log` and `swift-sdk` as root dependencies.
- `swiftLanguageModes: [.v5]` with Swift tools 6.1.
- A macOS platform declaration that does not prevent the existing Linux CI build.

`Dockerfile.headless` copies the root manifest, root lockfile, and the current portable source targets, then explicitly builds only the two existing executables. The release verifier and publication workflow enforce those binaries and the existing headless image behavior.

Putting SwiftCrossUI directly in the root manifest would make it part of the root package-resolution graph used by `swift package show-dependencies` in the headless Docker build. Even if SwiftPM avoided compiling the desktop target, this would unnecessarily couple the headless lockfile, Docker cache, and release source inputs to GTK UI dependencies.

A nested package avoids that coupling, but a nested package can consume only products exported by the parent package. Therefore `RepoPromptHeadless` must become an additive root library product.

## Existing runtime ownership and data flow

The current in-process flow is:

```text
arguments/options
  → HeadlessWorkspaceBootstrap.bootstrap
  → RepoPromptSession
      ├─ WorkspaceSelectionStateStore
      ├─ WorkspaceSessionStore
      └─ WorkspaceSessionRouter
  → HeadlessToolCatalog
      ├─ private tree/read/search implementation
      ├─ private selection mutation implementation
      ├─ private HeadlessWorkspaceContextBuilder
      └─ optional HeadlessOracleWorkflow
```

Selection mutation currently follows:

```text
HeadlessToolCatalog.manageSelection
  → resolve and validate paths/ranges
  → read WorkspaceSelectionStateStore snapshot
  → mutate WorkspaceSelectionSnapshot
  → persist(..., source: .headless)
  → serialize the resulting snapshot as MCP JSON
```

Provider-backed context follows:

```text
context_builder/oracle_send
  → snapshot selection once
  → HeadlessWorkspaceContextBuilder.build
  → reject incomplete context before HTTP
  → HeadlessOracleWorkflow.execute
      → concurrent Primary and Secondary provider calls
  → HeadlessToolCatalog serializes both lanes
```

The selection store and session are actors. `HeadlessToolCatalog` is also an actor, but its calls can re-enter while awaiting the selection store or provider. `HeadlessOracleWorkflow` deliberately starts both lanes concurrently from one immutable rendered context.

## Reusable code and the blocking boundary

The reusable implementation is already present:

- `HeadlessWorkspaceBootstrap` validates roots and establishes one session.
- `WorkspaceSelectionStateStore` is the authoritative selection owner.
- `HeadlessWorkspaceContextBuilder` implements secure rendering, omission reporting, byte budgets, slice handling, and symlink rejection.
- `HeadlessOracleWorkflow` preserves the two-lane prompt and result contract.
- `HeadlessOracleConfiguration.resolve()` provides the existing environment-only provider configuration.
- The CLI proves that one catalog can be composed directly in-process and retained for the process lifetime.

The blocker is that `HeadlessToolCatalog` exposes only:

```swift
public func tools() -> [Tool]
public func call(name: String, arguments: [String: Value]?) async -> CallTool.Result
```

Its useful typed implementations are private and its public operational boundary is MCP-shaped. A desktop adapter over `call` would have to create MCP `Value` objects, decode JSON text, reconstruct selection/context types, and duplicate the catalog’s error interpretation.

## Classic and CE references

Classic’s sidebar/detail layout is the appropriate workflow reference, but none of its implementation is reusable:

- It imports SwiftUI, AppKit, Combine, and macOS-specific controls.
- Its file tree, editor, presets, git/apply functionality, tabs, and Agent Mode exceed the requested scope.
- CE’s current root shell is also Apple-only and routes directly to its Agent Mode UI.

The portable desktop should copy only the conceptual split:

```text
left: workspace files and selection
right: instructions, selected context, provider action
```

# 3. Design

## 3.1 Targeted extraction, not a broader refactor

Use a targeted extraction inside `RepoPromptHeadless`. Do not move the context builder, Oracle provider, or session types into new targets. That would create a large source relocation and risk the mature headless contract merely to reduce a modest amount of transitive code in the desktop binary.

### Service-boundary decision

| Boundary | Decision | Rationale |
|---|---|---|
| Narrow public typed service shared by desktop and catalog | **Choose** | Preserves one in-memory session, actor ownership, exact selection semantics, and compile-time types. The catalog can retain its exact MCP serialization. |
| Desktop adapter over `HeadlessToolCatalog.call` | Reject | Couples UI state to MCP `Value`, JSON text, wire field names, and `CallTool.Result`; duplicates decoding and weakens error handling. |
| Subprocess JSONL or MCP connection | Reject | Creates a second process and lifecycle, separates session ownership, complicates cancellation and startup, and ships an unnecessary transport dependency. |

There is no runtime fallback between these boundaries. The desktop always uses the typed service in-process.

## 3.3 Typed workspace facade

### New public component

Add `public actor PortableWorkspaceService` to `RepoPromptHeadless`.

It is created once per catalog or desktop process and owns:

- The standardized real workspace roots.
- The existing `RepoPromptSession`.
- An injected `FileManager`.
- An internal path/index helper.
- One `HeadlessWorkspaceContextBuilder`.
- One optional `HeadlessOracleWorkflow`.

It does **not** own:

- A `WorkspaceSessionRouter`; binding remains a catalog concern.
- UI state.
- Persistence.
- Any MCP `Value`, `Tool`, or `CallTool.Result`.
- A subprocess or transport.

Illustrative public interface:

```swift
public actor PortableWorkspaceService {
    public init(
        roots: [String],
        session: RepoPromptSession,
        fileManager: FileManager = .default,
        oracleConfiguration: HeadlessOracleConfiguration? = nil
    )

    public func listFiles() async throws -> [PortableWorkspaceFile]

    public func applySelection(
        _ command: PortableSelectionCommand
    ) async throws -> PortableSelectionResult

    public func renderContext(
        maximumBytes: Int = 131_072
    ) async throws -> PortableRenderedContext

    public func executeOracle(
        _ request: PortableOracleRequest
    ) async throws -> PortableOracleExecution
}
```

Keep an internal initializer accepting `HeadlessOracleWorkflow?` so the current catalog provider fixtures remain injectable without changing existing test call sites.

### Public request and result types

Place these in `PortableWorkspaceModels.swift`.

#### File inventory

```text
PortableWorkspaceFile
- id: String                 // same as absolutePath
- absolutePath: String
- displayPath: String        // relative for one root, root[n]:relative for multiple
```

The UI always stores and mutates selection by `absolutePath`. `displayPath` is presentation only.

#### Selection

```text
PortableSelectionOperation
- get
- set
- add
- remove
- clear

PortableSelectionMode
- full
- slices
- codemapOnly               // raw contract spelling remains codemap_only

PortableSelectionSlice
- path: String
- ranges: [LineRange]

PortableSelectionCommand
- operation
- mode
- paths: [String]
- slices: [PortableSelectionSlice]

PortableSelectionResult
- snapshot: WorkspaceSelectionSnapshot
- selectedDisplayPaths: [String]
- autoCodemapDisplayPaths: [String]
- slicesByDisplayPath: [String: [LineRange]]
```

The service copies the existing `manageSelection` mutation rules exactly:

- Adding a full file removes that file’s slice and codemap-only state.
- Adding a slice removes codemap-only state and writes the supplied ranges.
- Adding codemap-only removes full and slice state and sets `codemapAutoEnabled = false`.
- Removing a path removes it from all three representations.
- Clearing replaces the state with a default `WorkspaceSelectionSnapshot`.
- Limits remain 1,024 selected files, 256 ranges per file, 4,096 total ranges, and 4,096 UTF-8 bytes per input path.
- Persistence remains `source: .headless`; no new selection-source case is needed.

The desktop uses only `add/remove` with `mode: .full` and `clear`. The richer command exists because the catalog must delegate its existing slice and codemap operations to the same implementation.

#### Context projection

Expose a stable, MCP-independent projection rather than making the internal builder type public:

```text
PortableRenderedContext
- roots: [String]
- selection: WorkspaceSelectionSnapshot
- entries: [Entry]
- omissions: [Omission]
- content: String
- contentByteCount: Int
- maximumByteCount: Int
- truncated: Bool
- omittedRootCount: Int
- completeForProvider: Bool
```

`Entry.Kind` cases:

- `selectedFull`
- `selectedSlice`

`Omission.Reason` cases must map one-to-one to the current internal cases:

- `outsideWorkspace`
- `symlinkEscape`
- `notFound`
- `directoryUnsupported`
- `invalidUTF8`
- `sourceTooLarge`
- `sliceOutOfBounds`
- `budgetExceeded`
- `readFailed`
- `orphanSlice`
- `invalidSlice`
- `autoCodemapUnsupported`

Use exhaustive `switch` mappings from the internal enums. Adding an internal omission reason later must fail compilation until the public projection is updated.

#### Oracle request and output

```text
PortableOracleMode
- chat
- question
- plan
- review
- proEdit

PortableOracleRequest
- mode: PortableOracleMode
- message: String
- reviewDiff: String?
- clarifyHandoff: String?
- maximumContextBytes: Int = 131_072
```

The service validates the existing limits and relationships:

- Message: non-empty after trimming, at most 65,536 UTF-8 bytes.
- `reviewDiff`: review-only, non-whitespace, no NUL, at most 262,144 bytes.
- `clarifyHandoff`: non-whitespace, no NUL, at most 1,048,576 bytes.
- Context budget: 1,024 through 1,048,576 bytes.

Public output deliberately excludes raw provider bodies, recovery objects, and bearer-sensitive metadata:

```text
PortableOracleExecution
- context: PortableRenderedContext  // exact context sent to both lanes
- pair: PortableOraclePairOutput

PortableOraclePairOutput
- pairID: UUID
- status: completed | partialFailure | failed
- primary: PortableOracleLaneOutput
- secondary: PortableOracleLaneOutput

PortableOracleLaneOutput
- lane: primary | secondary
- modelID: String
- status: completed | failed
- response: String?
- failure: PortableOracleFailureSummary?

PortableOracleFailureSummary
- code: String
- message: String
- httpStatus: Int?
- retryable: Bool?
- retryAfterSeconds: Int?
```

A Secondary success never replaces a Primary failure. Both lanes are always returned and displayed independently.

### Error type

Add:

```text
PortableWorkspaceServiceError
- code
- message
- incompleteContextDetails: PortableIncompleteContextDetails?
```

Stable code values used by both the desktop and catalog:

- `invalid_params`
- `path_outside_workspace`
- `not_found`
- `read_failed`
- `oracle_not_configured`
- `incomplete_workspace_context`

`PortableIncompleteContextDetails` contains the existing bounded diagnostic shape: truncation, omitted-root count, total omission count, first 64 omissions, and additional omission count.

Cancellation remains `CancellationError`; never wrap it as a workspace error.

### Internal detailed methods for the catalog

The service also has same-target internal methods:

```text
renderDetailedContext(maximumBytes:)
    → HeadlessWorkspaceContext

executeDetailedOracle(request:)
    → (HeadlessWorkspaceContext, HeadlessOraclePairResult)
```

The public methods project these internal results. `HeadlessToolCatalog` uses the detailed methods so its provider metadata and exact JSON shape remain unchanged.

This is not a second execution path: both public and detailed calls share one private rendering/Oracle implementation.

## 3.4 Shared path and file-index helper

Extract the following current catalog behavior into an internal `PortableWorkspacePathIndex`:

- Root standardization and symlink resolution.
- Relative, absolute, and `root[n]:relative` input resolution.
- Workspace-containment checking.
- Existing display-path formatting.
- Current file enumeration and skip policy.
- `shouldSkipName`.

This helper is used by both `HeadlessToolCatalog` and `PortableWorkspaceService`.

Keep the two path boundaries distinct:

1. `PortableWorkspacePathIndex` converts caller-visible path tokens to lexical absolute paths and display paths.
2. The existing private context-builder resolver and `HeadlessSecureFileReader` perform real-path and symlink safety checks at read time.

Do not merge these into `RepoPromptCore/WorkspacePathPolicy`; the root-qualified portable syntax and secure file-reading errors are specific to the headless product.

### Desktop inventory algorithm

`PortableWorkspaceService.listFiles()`:

1. Enumerates each root using the extracted current skip policy.
2. Does not read file contents.
3. Checks cancellation during traversal.
4. Rejects candidates whose resolved symlink target is outside every configured real root.
5. Deduplicates overlapping-root entries by absolute path.
6. Chooses the existing longest-root display representation.
7. Sorts by a stable case-folded `displayPath`, with the original path as the tie-breaker.

Complexity is `O(F log F)` time and `O(F)` memory for `F` discovered files.

The existing catalog’s `file_search` continues using raw enumeration order so no search-result ordering contract changes.

Do not expand `FileSystemProviding`; its current API lacks enumeration and metadata calls, and widening it would create unrelated conformer and test churn. Continue injecting `FileManager`, as the catalog already does.

## 3.6 Desktop application architecture

## Launch configuration

`PortableDesktopArguments` accepts only:

```text
--root <directory>          repeatable; --root=<directory> also accepted
--workspace-name <name>     optional; exactly once
--help
```

Behavior:

- No roots defaults to the process current directory through `HeadlessWorkspaceBootstrap`.
- Unknown arguments, missing values, empty values, and duplicate workspace names are usage errors.
- `--help` prints usage and exits successfully before creating a GTK application.
- Usage errors print to stderr and exit with code 64.
- There are no persistence, write, provider, model, backend, or feature flags.

The executable always passes:

```text
HeadlessOptions(
    roots: parsed roots,
    workspaceName: parsed name,
    persist: false
)
```

Provider configuration remains exclusively `HeadlessOracleConfiguration.resolve()`.

Resolve provider configuration before bootstrap, matching the CLI’s validation ordering. A malformed provider environment is a startup error; it is not silently downgraded to provider-free mode. An entirely absent provider configuration is valid and produces a local-only UI with the provider button disabled.

## Desktop backend seam

Define a UI-local exact protocol:

```swift
protocol PortableDesktopWorkspaceServing: Sendable {
    func listFiles() async throws -> [PortableWorkspaceFile]
    func applySelection(_ command: PortableSelectionCommand) async throws -> PortableSelectionResult
    func renderContext(maximumBytes: Int) async throws -> PortableRenderedContext
    func executeOracle(_ request: PortableOracleRequest) async throws -> PortableOracleExecution
}
```

`PortableWorkspaceService` conforms in the desktop module.

`PortableDesktopDependencies` follows the existing CLI dependency-injection pattern:

- `resolveOracleConfiguration`
- `bootstrap`
- `makeWorkspaceService`

The live implementation:

1. Resolves Oracle configuration.
2. Bootstraps one session.
3. Creates one service.
4. Reads the session snapshot for the workspace name.
5. Lists files.
6. Reads selection with a `.get` command.
7. Returns a loaded-workspace DTO without exposing the service to view state.

## Coordinator

`PortableDesktopCoordinator` is an actor. It owns:

- The launch configuration.
- The injected dependencies.
- The loaded service existential.
- A cached loaded-workspace result so repeated root-view tasks are idempotent.
- A coalesced startup task.
- At most one current Oracle `Task`.

Callable operations:

```text
load()
setFileSelected(absolutePath:selected:)
clearSelection()
renderContext()
generatePlan(instructions:)
cancelOracle()
```

`generatePlan` always constructs:

```text
mode: plan
reviewDiff: nil
clarifyHandoff: nil
maximumContextBytes: 131072
```

There is no mode picker and no fallback to chat, question, or Pro Edit.

## View state

`PortableDesktopState` is a value type held by `@State` in the root view. Do not use Combine or `ObservableObject`.

State includes:

```text
launch phase:
- idle
- loading
- ready
- failed(message)

workspace:
- name
- roots
- files
- searchText
- selected absolute-path set
- selected display paths
- Oracle availability and model IDs

editor:
- instructions

selection operation:
- idle
- updating(operationID)

context preview:
- idle
- loading(operationID, previous?)
- ready(PortableRenderedContext)
- failed(message, previous?)

Oracle:
- unavailable
- idle
- loading(operationID, previous?)
- ready(PortableOracleExecution)
- failed(message, previous?)
- cancelled(previous?)
```

Only the coordinator retains service actors and tasks. No secret, bearer token, URLSession, session actor, or workspace service enters `@State`.

## State transitions and ordering

| Trigger | Data path | Result |
|---|---|---|
| Initial `.task` | View → coordinator → configuration → bootstrap → service → file inventory/selection | Replace launch state atomically with ready or failed. Repeated task execution reuses the same coalesced load. |
| Search edit | Search binding → state only | Recompute visible files locally; never mutate selection or touch disk. |
| File row click | Absolute path → coordinator → `.add/.remove`, `.full` → selection store | Replace the entire UI selection from the authoritative returned snapshot. No optimistic mutation. |
| Clear | Coordinator → `.clear` → selection store | Replace authoritative selection and invalidate context/Oracle output. |
| Instructions edit | Binding → state | Preserve context preview; invalidate prior Oracle output because it used different instructions. |
| Preview | Coordinator → service → immutable selection snapshot → context builder | Show content and omissions even when incomplete. |
| Generate Plan | Coordinator → service → immutable context → dual Oracle lanes | Show the exact context used and both independent lane outputs. |
| Cancel | View → coordinator → cancel current Oracle task | Existing successful output remains available; current operation becomes cancelled. |

Every async operation receives an operation UUID. A completion updates state only if its UUID still matches. This prevents a cancelled or stale completion from overwriting a later operation.

While a selection mutation is active, selection controls are disabled. While Oracle generation is active, selection controls and the instructions editor are disabled, and a Cancel button is shown. Duplicate clicks while an operation is active are ignored.

All `@State` writes occur on the main actor. The coordinator and workspace service execute on their own actor executors. Context rendering performs synchronous filesystem work on the service actor, not the UI executor. The existing Oracle workflow retains its concurrent lane execution and URLSession cancellation behavior.

## 3.8 Error and edge-case behavior

- **Missing or invalid root:** startup error; no partial workspace.
- **Missing provider configuration:** local preview works; Generate Plan is disabled with configuration guidance.
- **Malformed provider environment:** startup error, matching CLI behavior.
- **Empty instructions:** Preview remains allowed; Generate Plan is blocked locally with an inline validation message.
- **Empty selection:** valid; context states that no readable files are selected, matching current headless behavior.
- **Non-UTF-8, oversized, missing, directory, unsafe symlink, invalid slice:** Preview displays omissions. Provider calls fail before HTTP through `incomplete_workspace_context`.
- **File removed after inventory:** do not silently remove it from selection. Preview reports `not_found`; Clear Selection remains available.
- **Overlapping roots:** inventory deduplicates by absolute path and uses the longest matching root display label.
- **Partial Oracle failure:** render both lanes and pair status. Do not turn it into a generic UI failure.
- **Both Oracle lanes fail:** render both failures and `failed` pair status.
- **Cancellation:** propagate `CancellationError`; do not expose it as `execution_failed`.
- **Window/process exit:** there are no persistent workers or open file handles. Process termination releases the session, URLSession, and GTK resources. The explicit Cancel action handles normal in-app cancellation.

# 5. Risks and migration

There is no data migration. The relevant risks are implementation and release isolation:

- **Catalog regression:** moving selection/context orchestration can accidentally change validation ordering or error text. Mitigation: retain parsing in the catalog, move only typed mutation/execution, and run the entire existing catalog suite unchanged.
- **Root graph contamination:** an accidental root SwiftCrossUI dependency would affect Docker resolution. Mitigation: nested package plus an explicit negative root-graph assertion.
- **SwiftCrossUI API mismatch:** the implementation must target exactly 0.8.0 and only the supplied stable APIs. A compile failure is fixed against that pinned API; do not add an alternate backend or conditional fallback.
- **GTK runtime omission:** a successfully compiled binary may fail on a clean host. Mitigation: `ldd` verification, documented packages, and an actual Xvfb launch.
- **Resource bundles:** SwiftPM dependencies may emit resource directories. The packaging script copies all emitted resource bundles adjacent to the executable rather than assuming a single-file package.
- **Existing dirty worktree:** implementation must not reset, clean, reformat, or overwrite unrelated changes. Capture protected diffs before work and compare them after every atomic step.
- **Rollback:** because there is no persisted data, rollback is source-only. Revert the service/catalog refactor atomically, remove the nested package and additive root product, and leave the existing headless release artifacts untouched.
